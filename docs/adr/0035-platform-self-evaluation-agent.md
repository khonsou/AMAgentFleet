# ADR-0035：统一平台评测 Agent、确定性评分与有界自迭代

- **状态**：已接受
- **日期**：2026-11-01

## 背景

Fleet 已有统一 Task Pool、RuntimeAdapter、指挥官与操作助手，但项目完成度仍主要靠功能清单和测试结果描述，缺少独立、可持续的平台评估。开发评测、发布后运行监控与第三方业务评估若混为一谈，会用第三方业务 KPI 代替平台能力，也容易让评测建议自动触发无尽开发。真实多 Agent 实测已证明需要同时记录质量、成本、恢复和人工介入。

## 决定

1. **唯一评测身份**：内置 `fleet-eval-01`，负责开发时平台验收和发布后只读运行监控；不设置第二个平台评测 Agent 或独立场景身份。它注册在 Agent Registry，但不能承接普通业务 worker Task，不评价第三方业务 KPI。
2. **场景与 Agent 分离**：版本化场景、受控数据、预期事实、评分规则和停止条件放在 `evals/platform/`；场景只是 Agent 的输入。开发／评测输出写 `artifacts/platform-evals/` 或部署对象存储，不写回场景目录。
3. **确定性评分**：平台按 Task Pool 与 Goal 编排、多 Agent 协作、统一协议、Runtime 复用、共享 Evidence 与授权、Playground、工程质量与成本七个维度评分。`fleet-eval-01` 组织评测和解释证据，分数由确定性评分器计算；模型不得给自己打分。
4. **证据复用与持久化**：真实执行复用 `fleet_task_loops`、Thread／Run；结构化评分与基线对比进入 `fleet_eval_reports`；建议及其处理状态进入 `fleet_eval_recommendations`。大型证据只保存到 artifact store，数据库保留摘要与引用，秘密正文不得进入任何记录。
5. **两种工作模式**：开发评测在 PR、发布候选或人工触发时比较候选版本与基线；发布后持续采集运行指标，按周期或异常触发只读分析。生产不执行负载测试，不因持续监控持续调用模型。
6. **有界开发迭代**：建议状态固定为 `proposed → accepted/rejected → implemented → verified/closed`，禁止 `proposed → implemented` 自动跳转。只有维护者接受的建议才能形成一次开发改动；复测只能关闭或标记失败，不能自动启动下一轮。
7. **停止条件**：达到当前发布门、连续两轮无净改善、同一失败假设重复、达到时间／Token／实验预算、缺少新的可验证假设或维护者停止时，必须结束本轮。MVP 首先追求硬门全过与 75 分，不默认追求 100 分。
8. **第三方边界**：第三方 Agent 的业务 Goal、领域 Evidence 与业务评分由运营方负责。平台只验收其注册、执行、恢复、隔离、证据和权限契约是否可复用。

## 后果

- 正面：平台质量、成本和运行趋势可用同一口径持续比较；评测 know-how 可版本化、可审计；建议不会自动放大为无限任务。
- 负面／约束：需要维护场景、基线和报告 schema；真实模型评测仍有成本，必须按预算触发。
- 实施边界：首批只实现场景 schema、确定性评分器、建议状态机和停止条件测试；生产监控、自动唤醒业务链路和评测 GUI 分别验收，不在首批隐式完成。

## 已考虑的备选

- **仅使用 CI 测试脚本**：否决，无法形成发布后的运行趋势与版本化改进建议。
- **评测 Agent 自主修改并复测平台**：否决，容易无限迭代、放大副作用并混淆验收权。
- **第三方业务评分直接作为平台评分**：否决，业务成效与平台通用能力不是同一评价对象。
- **所有报告只存 Agent 私有记忆**：否决，无法独立审计、比较版本或防止记忆污染。
