# ADR-0029：Fleet Run 预算、幂等派发与断点恢复

- **状态**：已接受
- **日期**：2026-10-29

## 背景

舰队指挥官在第 7 个模型轮次、已经完成 3 次 `agent_spawn` 后触达 DeerFlow 默认
`recursion_limit=100`。这不是业务死循环：LangGraph 的中间件与工具节点使每次模型轮次
消耗多个 graph step，五路派发在收尾前耗尽预算。原实现还有两个放大问题：

1. Dispatcher 未显式传递 Run 预算，失败只回 `claimed`，用户只能从头重跑。
2. 重跑会再次追加原始 HumanMessage，并可能重复创建已成功的子任务。
3. 临时网关故障、权限／配置错误和递归预算耗尽没有区分；缺少有上限的自动恢复和
   用户可操作的断点续跑。

## 决定

1. **Run 预算显式化**：Fleet Run 默认 `recursion_limit=300`，可用
   `FLEET_RUN_RECURSION_LIMIT` 调整；保留 DeerFlow 自身硬上限，不默认拉到最大值。
2. **派发副作用幂等**：`agent_spawn` 以父 Thread、`spawn_key or assignee` 和完整子任务
   输入生成稳定幂等键，同时写入 Task 与 HTTP `Idempotency-Key`。同一父 Thread 重试
   同一子任务返回原 Task；确需创建同文但不同的任务时，调用方必须提供不同 `spawn_key`。
3. **异常分类**：
   - `recursion`：预算耗尽；有 checkpoint 时自动断点续跑最多 1 次。
   - `transient`：传输错误及明确的临时 HTTP 状态；自动重试最多 2 次，分别退避
     2 秒、10 秒。
   - `permanent`：权限、参数、配置及未识别错误；不自动重试，保留错误供人工处理。
4. **断点续跑不重复输入**：resume 使用最近 `checkpoint_id`，请求 `input=None`；
   retry 则把原始任务作为新指令追加到当前 Thread。成功交付后清理恢复现场。
5. **人工恢复入口**：Console 与 FAP 同时提供“从断点继续”和“重新执行”。人工断点
   续跑总上限 3 次（包含自动续跑）；已有恢复动作排队或正在运行时拒绝重复启动。
   老 Loop 未保存 checkpoint 时，后端向 Gateway 补取，无需用户修数据。
6. **可观测性**：Loop 记录异常类别、重试／续跑次数、下次重试时间、恢复动作和最近
   checkpoint；Task 详情显示已创建子任务，便于恢复前核对实际进度。不新增 Task／Loop
   业务状态。
7. **重启语义**：新 Loop 和已持久化恢复动作的 Loop 自动恢复；永久错误不因服务重启
   被隐式重放。reaper 保留崩溃 Run 原来的 retry／resume 语义。

## 后果

- 五路及更复杂编排有合理预算；达到预算后仍可从现场继续，不必从头消耗 token。
- 自动恢复有明确次数上限，不会把永久性错误变成重试风暴。
- 幂等键避免重复子任务，但同文独立任务必须显式提供 `spawn_key`。
- 进程内延迟队列仍受单实例门闩约束；多副本 active-active 不在本次范围内。

## 已考虑的备选

- **只把 recursion limit 提到 1000**：否决。会掩盖失控循环，且不能解决重复副作用和
  临时故障恢复。
- **所有异常统一自动重试**：否决。权限和配置错误重试无意义，并增加成本与噪声。
- **resume 也重新发送原始输入**：否决。会诱导模型重新规划并重复已完成副作用。
