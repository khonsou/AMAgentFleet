# ADR-0034：人类消息乐观上屏与异步 Agent 执行

- **状态**：已接受
- **日期**：2026-11-01

## 背景

ThreadDetail 的正确交互是先展示人类输入，再等待 Agent 返回。Playground 的 Bot 对话与 Task 群聊此前在 `await execute(...)` 期间不上屏，并用 `sending` 或全局 `busy` 阻止再次发送，混淆了消息发送与 Agent 执行状态。直接连续发送还可能因 `threadId` 尚未更新而重复创建 Thread，或被后续消息快照覆盖乐观消息。

## 决定

1. **人类输入立即上屏**：发送后立即把内容追加到当前对话并清空输入框，不等待 Thread 创建、Run 或 Agent 回复。按钮只受“输入是否为空”约束，不因上一条仍在执行而禁止下一条。
2. **执行状态按消息表达**：乐观消息使用 `sending`／`failed` 状态；Agent 回复和错误在后台独立返回，不把全局忙碌状态用于长时间 Agent 执行。
3. **首次创建去重**：首次发送与后续等待者共用一个 Thread 创建 Promise，并显式区分创建者与后续发送者。首条由 `threads.create` 携带指令，后续消息通过 `threads.send` 续接，避免重复创建和消息丢失。
4. **快照合并而非覆盖**：服务端消息与未确认乐观消息合并，按角色／actor 与内容去重；轮询不得删除仍在执行或失败的消息。响应顺序以实际执行完成为准，不承诺并发 Run 的返回顺序。
5. **协议写语义不变**：`confirmed: true`、幂等、服务端 actor 和审计不变；本决策只统一 GUI 消息呈现与异步执行方式。回归覆盖连续发送、首次创建竞争、慢响应和快照去重。

## 后果

- 正面：Playground 与 ThreadDetail 的交互一致，连续协作不再被等待锁阻断，也不会因状态竞争重复建 Thread。
- 负面／约束：需要保留每条乐观消息的状态与去重逻辑；并发执行的后端完成顺序可能不同，页面不得承诺乱序回复的确定性。
- 安全：没有扩大工具权限或放宽写操作校验；失败消息保留并可诊断，不静默丢弃。

## 已考虑的备选

- **等待 Agent 返回后再显示人类消息**：否决，用户无法确认输入是否已发送，且会被长任务锁住。
- **仅用 sending 禁止再次发送**：否决，破坏连续对话与异步协作。
- **每次发送都创建新 Thread**：否决，破坏持久会话与上下文连续性。
- **用服务端快照直接覆盖乐观消息**：否决，会造成发送中消息消失或重复。
