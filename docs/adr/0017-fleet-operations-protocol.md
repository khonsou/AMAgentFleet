# ADR-0017：Fleet 全量操作协议与默认操作 Agent

- **状态**：已接受
- **日期**：2026-10-28

## 背景

Fleet 已包含 Agent 定义与生命周期、Task／Loop、Thread／Run、验收、Inbox、cron、MCP、模板、审计和 PAT 等操作。页面交互复杂，但现有 FAP 文档与 Console 私有视图并不完整；若为少数自然语言场景逐个定制流程，会迅速产生新的能力分叉。需要一份覆盖全部可操作功能的协议，并让默认注册的操作 Agent 与第三方 Agent 共用。

## 决定

1. 以 `fleet-ops-protocol.json` 作为唯一操作清单：每项包含稳定 operation ID、服务面、HTTP 方法、路径、参数示例、读写属性与确认级别；`GET /api/ops/protocol` 自发现，`/api/meta` 指向它。
2. 默认注册 `fleet-ops-01`，通过专属 `fleet:ops` 工具组调用清单操作。工具按 operation ID 解析路径，不允许模型任意请求内网地址；其他 Agent 不继承该权限。
3. 读操作可直接执行；所有写操作必须经用户明确确认。PAT 签发及非空 `secrets` 配置为 human-only，秘密不得进入 Agent Thread；其余能力不按自然语言场景裁剪。
4. 浮窗对话只是 `fleet-ops-01` 的 Web Thread，不为每句聊天创建业务 Task。业务 Task／Loop、交付验收、审计及现有 API 状态机保持不变。
5. 协议覆盖性由测试约束：Control Plane 的所有 API 路由必须在清单中登记；新增操作必须同步协议，不能只加页面或端点。

## 后果

- 正面：网站全能力获得统一、机器可读的人机操作面；自然语言入口与第三方 Agent 不再依赖预设闭环；协议缺项可自动发现。
- 负面/约束：操作清单成为所有新功能的必改文件；`fleet-ops-01` 是高权限内部 Agent，必须维持专属工具组、写确认和秘密隔离。

## 已考虑的备选

- **按常见对话场景逐个实现**：否决，覆盖不全且会形成重复业务逻辑。
- **给操作 Agent 通用 HTTP 与全内网访问**：否决，绕过操作级审计、确认和出口边界。
- **为每个操作分别制造工具**：暂不采用；稳定 operation ID + 统一执行器已足够，避免数十份重复包装。
