# ADR-0030：指挥官显式指派与引导式断点恢复

- **状态**：已接受
- **日期**：2026-10-29

## 背景

指挥官把 `assignee` 留空作为常见选择，导致已注册 worker 存在时，子任务仍全部停留在开放任务池，父任务却已经结束编排。另一方面，ADR-0029 的 `input=None` 断点续跑会原样恢复导致递归上限的状态；实测同一 Ops Thread 两次续跑各重复读取 `system.protocol` 23 次，无法收敛。

## 决定

1. **显式指派为默认**：指挥官在用户未指定执行者时先读取一次可用 Agent 清单，为每个 `agent_spawn` 选择合适且处于 `registered/running` 的 worker。只有用户明确要求开放抢单时才允许 `assignee` 留空；无合适 Agent 时报告能力缺口，不静默制造待分配任务。
2. **操作助手不承接业务 worker 任务**：`fleet-ops-01` 只负责平台操作；指挥官也不得把子任务派给自己形成环。
3. **恢复指令替代原样重放**：修订 ADR-0029 第 4 条。checkpoint 续跑仍不得重复原始任务输入，但应追加一条恢复指令，要求模型利用已有结果、只执行必要的未完成步骤；能力或权限反复不可获得时停止工具调用并交付真实阻塞原因。
4. **保留底层保险丝**：`recursion_limit=300` 与恢复次数约束不变，不用提高硬上限掩盖循环，也不新增更小的人为轮次限制。

## 后果

- 默认编排会真实拉起可执行 worker，而非只创建待分配 Task；开放抢单仍有明确用途。
- 恢复指令为模型提供跳出旧工具循环的新上下文，同时保留 checkpoint、已有工具结果与幂等保护。
- 引导式恢复不能修复错误指派或缺失工具本身；此类任务应如实交付阻塞原因，再由指挥官改派合适 Agent。

## 验证

- 同一旧 checkpoint 原样续跑连续两次各重复 23 次协议读取；加入恢复指令后不再调用工具，直接交付能力缺失说明。
- 自动化回归覆盖恢复请求不包含原始任务、包含收敛指令，以及指挥官默认显式指派策略。
