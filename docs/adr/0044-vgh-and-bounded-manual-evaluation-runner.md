# ADR-0044：VGH 北极星、单 Agent 对照与有界手动评测启动器

- **状态**：已接受
- **日期**：2026-11-02

## 背景

ADR-0035 已确定统一评测身份、确定性评分和有界建议状态机，但还缺少可重复的真实执行入口。仅比较七维分数容易把迭代变成“围绕评分表做功能”，也无法证明多 Agent 相对单 Agent 的净收益。真实 GEO Canary 另有两轮复测需求，但不能把业务变化误当平台改善或 GEO 因果。

## 决定

1. **北极星为 VGH**：以“每人类小时交付的独立验收 Goal 数”衡量价值。VGH＝60×已验收 Goal 数÷主动人工分钟。人工时间包括配置、发起、催促、修复、恢复和验收；等待时间只计墙钟。未记录人工时间时 VGH 为 `null`，不得按零分钟计算。
2. **Goal 与验收不可拆分刷量**：一次完整参考工作流是 1 个 Goal，子 Task 不单独计数；失败、超时、部分交付和未独立验收均不计为已验证 Goal。
3. **同协议单 Agent 对照**：`core-v1` 启动器必须同时支持 `single` 与 `multi`，使用同题、同 fixture、同模型 Profile、等价预算和相同独立验收。`single` 只生成技术基线，不得持久化为平台候选报告。
4. **手动单轮入口**：`POST /api/eval/runs` 与 `scripts/fleet_eval_run.py` 只在维护者显式调用时执行。入口支持幂等续跑、真实 Task／Loop／Thread、Token、墙钟、人工事件、结构化执行状态和产物哈希；不启用 cron，不因报告生成自动启动下一轮。
5. **独立硬门证据**：P1 只能来自协议／Runtime／安全证据，P2 只能来自非工程用户核心路径验收，缺省均为 false；不得由 Agent 自评填通过。七维评分继续由确定性评分器计算，`fleet-eval-01` 只解释结果并提出 `proposed` 建议。
6. **实施与复测可追溯**：建议 transition 可携带 `implementation_commit`、`candidate_report_id` 和改动摘要，同时保持既有状态机与人工 accept 门。禁止自动开发、自动合并和自动接受建议。
7. **真实 Canary 两轮分离**：第一轮技术交付不等于 Owner 验收。第二轮必须提供第一轮闭合回执和 Owner 接受文件；最终 VGH 还需要最终 Owner 验收与实测主动人工时间。观测变化不作 GEO 因果归因。
8. **总预算是硬边界**：预算停止不得继续派发新任务，必须请求取消活动 Runtime 并保存取消回执。解释任务和交付回执自身也计入 Token 与墙钟；超额、交付失败或缺少安全证据不得被 Owner 批准掩盖为平台成功。
9. **verify 必须有严格 improve**：候选报告必须同时满足 P0–P2 与可比基线要求、达到场景目标分、VGH 严格大于基线，并且未授权 Effect／秘密泄漏为零、质量／成本／安全护栏不退化。VGH 持平、下降、缺少人工计时或护栏证据均不得通过 verify；该判断由确定性评分器输出 `release_allowed`，transition 强制执行。

## 后果

- 正面：平台评分重新服务于真实价值，单 Agent 对照可证明多 Agent 是否值得保留；真实执行、人工决策和复测证据可审计。
- 负面／约束：需要维护人工计时、独立验收和基线兼容性；同步手动入口在长任务上需要调用方保持请求，后续如有真实需求再另写 ADR 设计持久 watcher。
- 本批边界：只完成实现与离线验证，不宣称真实单 Agent 基线、生产监控、Evaluations GUI 或 GEO 两轮闭环已完成。

## 已考虑的备选

- **只用七维评分驱动迭代**：否决，无法表达人类时间和已验证结果的价值。
- **只跑多 Agent 候选**：否决，无法证明协调成本带来净收益。
- **报告生成后自动创建开发 Task**：否决，违反 ADR-0035 的有界维护者门。
- **真实两轮连续自动执行**：否决，绕过第一轮业务 Owner 验收，容易把失败放大为无效复测。
