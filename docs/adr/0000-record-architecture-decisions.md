# ADR-0000：使用 ADR 记录架构决策

- **状态**：已接受
- **日期**：2026-10-08

## 背景

项目已立项，涉及 harness 选型、协作模型、授权模型等多个影响深远且需要向团队（含未来的维护者和 AI 编码助手）解释"为什么"的决策。设计文档回答"做什么"，但决策的备选方案和否决理由会随时间丢失。

## 决定

采用轻量 ADR（Architecture Decision Record）记录所有重要架构决策：

1. 存放于 `docs/adr/`，文件名 `NNNN-kebab-case-title.md`，顺序编号、永不复用。
2. 格式固定为四节：**背景 / 决定 / 后果 / 已考虑的备选**（Nygard 简化版），单篇控制在 1 屏以内。
3. 状态流转：`提议中 → 已接受 / 已否决 / 已被 ADR-XXXX 取代`。ADR 内容不可变，推翻旧决策只能写新 ADR 并互链。
4. 以下变化必须配 ADR：harness 底座变更、授权模型变更、数据模型破坏性变更、引入/移除核心依赖、基础设施形态变更。
5. 设计文档（`deepseek-agent-fleet-mvp-design.md`）保持"当前真理"，ADR 保持"决策历史"；两者冲突时以最新 ADR 为准并回改设计文档。

## 后果

- 正面：决策可追溯；新人与 AI 助手读 ADR 即可理解约束；评审有锚点。
- 成本：每次重大变更多写半页纸。

## 已考虑的备选

- 只维护设计文档：否决，"为什么否决了 X"的信息会丢失。
- 用 Git commit message 记录：否决，难以检索和汇总当前有效决策集。
